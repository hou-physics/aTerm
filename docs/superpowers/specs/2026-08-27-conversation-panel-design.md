# 对话面板（快照预览 + 时间线目录）设计文档

日期：2026-08-27
状态：已与项目所有者逐项确认（内容边界、界面形态、性能预算、三项代行决定均已确认）
所属：P2 子项 A（P2 拆分为 A 对话面板 / B 状态引擎 / C 总览方块页，本文档只覆盖 A）

## 1. 目标

在终端右侧提供一个可隐藏的对话面板，解决"上下文特别长时找不到之前说过什么"的问题：

- **秒开**：不启动 `claude` 进程即可阅读任意会话，包括**从未运行或已结束的历史会话**
- **零成本**：不消耗 token，不产生任何模型调用
- **可定位**：按日期分组的时间线列出用户发起的每一轮，点击跳转到正文对应位置

**非目标**
- 不在面板里与 Claude 交互（交互仍在左侧终端）
- 不渲染工具调用的输入输出（见 §3 内容边界）
- 不做实时自动跟随（推迟到 P2b，见 §8）

## 2. 关键约束（决定了整个设计）

**Claude Code 的 TUI 运行在备用屏幕缓冲区（alt-screen），并启用全动作鼠标追踪（`CSI ? 1003 h`）。**

实测证据（aTerm 内置 ⌘⇧D 诊断，真实会话）：
```
[aTerm 诊断] buffer=alternate mouse=any appCursor=false rows=47 cols=125 cellH=15.0 fontSize=13
```

由此产生两条硬约束：

1. **alt-screen 没有回滚缓冲**，终端侧不存在"历史位置"这一概念
2. **滚动由 Claude 自己掌管**，外部既无法把画面滚到指定位置，也无法得知某条消息在其内部滚动中的坐标

因此**"点目录让终端跳转"不可实现**——不是工程量问题，是没有接口。设计的应对是：**面板自身即阅读面**，数据来自会话记录文件而非终端。这一转向同时带来了读取历史会话的能力。

## 3. 内容边界

面板只呈现**对话正文**：用户发起的每一轮 + Claude 的回答文字。工具调用（`tool_use`）与工具结果（`tool_result`）**完全不呈现，也不解析**。

依据（实测于本机最大会话 63.2MB）：

| 项 | 数值 |
|---|---|
| 文件体积 | 63.2 MB |
| 正文字符 | 444 k（占体积 **0.7%**） |
| 可渲染条目 | 约 720 条（用户轮 + 回答段） |
| 工具调用 / 结果 | 1081 / 1081 次，占据几乎全部体积 |

## 4. 数据层（Rust）

新增 `src-tauri/src/sessions/conversation.rs`，公开一个 Tauri 命令：

```rust
#[tauri::command]
pub fn read_conversation(dir_name: String, root_key: String) -> Result<Conversation, String>
```

返回结构（serde camelCase）：

```rust
pub struct Turn {
    pub role: String,      // "user" | "assistant"
    pub text: String,
    pub ts_ms: i64,
    pub uuid: String,      // 正文锚点与时间线条目的关联键
}
pub struct Conversation {
    pub turns: Vec<Turn>,
    pub files: Vec<String>,
    pub total_bytes: u64,
}
```

**解析规则**（顺序即优化顺序）：

1. 定位该项目目录下属于此会话链（`root_key`）的全部 jsonl 文件，按时间升序拼接。分组规则复用 `sessions/scan.rs` 既有的链分组逻辑（按首条用户消息 uuid 分组），不另起一套
2. 逐行**字节扫描筛选**，满足任一条件即跳过、不做 JSON 解析：
   - 行内含 `"tool_result"`（工具结果，体积主体所在）
   - 行内不含 `"type":"user"` 且不含 `"type":"assistant"`
3. 对剩余候选行做 JSON 解析，提取文本：
   - `message.content` 为字符串 → 直接取用
   - 为数组 → 取其中**全部** `type=="text"` 项的 `text`，以换行拼接为**一条** Turn（一条记录最多产生一条 Turn）
   - 数组中的 `tool_use` 项忽略即可，**不因其存在而丢弃整条记录**

**为何不按 `"tool_use"` 过滤整行**（实测结论，勿"优化"回去）：该串会与正文内容碰撞——任何正文里提到 `tool_use` 的消息都会被误杀。实测最大会话中，按 `tool_use` 过滤会静默丢失 **24k 字符（约 5%）** 的真实正文；而保留这些行仅多花 4 ms（Python）/ 约 1 ms（Rust）。此外它还能抵御未来格式变化（若某版本开始把 text 与 tool_use 放进同一条 assistant 记录，激进规则会整段丢失回答）。当前版本实测两者不混排（1045 条纯正文 / 1928 条纯工具调用 / 0 条混排），但该结论不作为设计依赖。
4. 丢弃 `isSidechain == true` 的记录（子代理对话不属于主线）
5. 丢弃注入文本（`<` 或 `Caveat:` 开头，沿用标题解析的既有规则）
6. 丢弃 trim 后为空的轮次

**缓存**：以 `(路径, 大小, 修改时间)` 为键缓存解析结果。文件仅追加增长时，从上次解析偏移继续，不重扫已解析部分。

**读取上限**：本模块与标题解析不同，**需要完整扫描文件**（正文分布在全文）。这是有意为之：§3 的实测表明筛选后的解析量仅占 10% 行数，代价可接受。会话索引（`parser.rs`）的头尾有界读取规则不变，两者互不影响。

## 5. 性能预算

实测基准（63.2MB 最大会话，Python 实现，Rust 预期再快 5–10 倍）：

| 策略 | 耗时 |
|---|---|
| 全量 JSON 解析 | 129 ms |
| **字节筛选 + 按需解析（采纳方案）** | **74 ms**（7057 行中解析 2880 行，抽出正文 468k 字符） |

**验收标准**：最大会话（63.2MB）首次打开，Rust 侧解析 **< 50 ms**；命中缓存 < 5 ms。

（实测命中缓存耗时 1.7–2.0ms，主要由 `group_chain_files` 在每次调用时重扫目录链拓扑构成——真正的正文解析缓存命中本身接近零开销。是否再加一层目录拓扑缓存被判断为不值得：当前版本没有自动轮询/跟随，重复调用只发生在手动刷新或切标签时，不是高频路径；此项记录为 P2b 实时跟随若使这条路径变热时的候选优化项。）

**轻量纪律**（强制，写入实施计划的验收项）：

1. 永不解析工具输出
2. 解析在 Rust 侧完成，仅将抽取后的正文传给前端
3. 按文件缓存，重复打开零成本
4. 运行中的会话只解析新追加字节
5. **第一版朴素文本渲染**——不做 Markdown 解析、语法高亮、代码块着色。真正的重量风险在渲染而非解析，此项优先级高于视觉精致度

## 6. 界面（前端）

新增 `src/components/ConversationPanel.tsx`，停靠终端右侧。

**布局**（展开态；拖拽手柄在面板左边缘，图中未画出）
```
┌──────────────────────────┬────────────────┐
│                          │ 标题        ⟳ │
│   终端（左，保持原样）      ├────────────────┤
│                          │ 8月27日        │
│                          │   14:32 摘要…  │
│                          │   12:19 摘要…  │
│                          │ 8月26日 (3)    │
│                          ├────────────────┤
│                          │ 正文（可滚动）   │
└──────────────────────────┴────────────────┘
```
收起态：面板整体不渲染、不占用任何宽度（不是收成一条竖条），终端拿满剩余空间。**首次启动
（本地尚无 `panelCollapsed` 持久化偏好）默认即为收起态**，不在冷启动时抢占注意力；一旦用户
通过 TabBar 按钮或 ⌘J 收起/展开过一次，该偏好即写入 `localStorage`，之后启动直接读取已保存
的值（无论收起还是展开），不再套用这个首次默认值——细节见 §9 第 5 条。

- **宽度可由用户拖拽调节**（P2a 后续迭代根据实测反馈加入，见 §9）：默认 400px，拖拽范围
  [280, 900]px，且不超过窗口宽度的 60%（拖拽/双击复位时现算，不装 window resize 监听器）；
  拖拽手柄在面板左边缘，用 pointerdown/move/up + `setPointerCapture` 实现，不依赖全局
  mousemove 监听器；宽度持久化到 `localStorage`（`aterm-panel-width`），沿用 `store/layout.ts`
  既有的 try/catch 读写模式，`pointermove` 期间只更新内存、`pointerup` 才落盘；双击手柄复位到
  400px（同样过 60% 窗口宽度上限，窄窗口下可能小于 400，是有意为之）
- **收起/展开只有一个入口**：TabBar 右端的开关按钮，双向工作（收起⇄展开），与 **⌘J** 共享
  同一个 `panelCollapsed` 字段（`store/layout.ts`，持久化到 `localStorage`，沿用既有
  try/catch 读写模式）——这是唯一真相来源。~~面板头部曾自带一个折叠按钮（›），与 TabBar
  按钮、⌘J 三处共享同一字段~~：用户反馈两个收起入口冗余，已删除，不引入第二个标志位；细节
  见 §9 第 4 条
- 另有 **Ctrl+Tab / Ctrl+Shift+Tab**：在标签间循环切换（含主页标签，越过数组两端回绕，
  行为对齐 Chrome）。实现在 `App.tsx` 既有的窗口级 `keydown` 监听器里，不新增第二个监听器；
  该监听器现改为**捕获阶段**注册（`addEventListener(..., true)`），确保这两个组合键不会先被
  终端（xterm）吃掉，只对命中的组合调用 `preventDefault`/`stopPropagation`，其余按键不受影响
- 展开/收起、拖拽调宽都会改变终端可用宽度，须触发既有的 ResizeObserver 重排路径（不得改动该路径本身）

**时间线**
- 按本地日期分组，组标题形如 `8月27日`，**不带任何前置符号**（用户明确不要图形提示）；
  标题仍是可点击的 `<button>`（保留 `aria-expanded`），可点性以 `cursor: pointer` 与清晰的
  hover 背景/字色变化传达，折叠态靠标题旁的 `(n)` 计数与间距辨认，不在右侧另加指示符
- **默认只展开最新一天**（列表第一组），其余日期分组折叠，折叠时标题旁显示该组条目数；
  展开状态存在组件自身 state 里，不持久化，随会话数据每次替换（切标签、手动刷新）重新播种
- 每条对应一个**用户发起的轮次**：`HH:MM` + 首行摘要（截断），用固定缩进表达"属于该日期
  分组"的层级关系，不用圆点符号
- 点击 → 正文区滚动到该轮（以 `uuid` 作为 DOM 锚点）
- **时间线区域整体可拖拽调高、可双击折叠**（P2a 后续迭代加入，见 §9 第 6 条），与上面
  "单个日期分组折叠"是两套彼此独立的机制——那一条只影响某一天的条目是否展开，不改变时间线
  区本身占多高；这一条改的是整块时间线区（含全部日期分组）在面板里的高度，用意是让正文区能
  在需要时占满面板剩余高度。时间线区与正文区之间新增一条水平分隔条：
  - **拖拽**分隔条调整时间线区高度，范围 [80px, 内容区高度的 60%]（60% 是动态量，只在
    拖拽这一刻现算，不装 resize 监听器，同 §6 宽度手柄的 `windowCap` 是同一思路，实现在
    `ConversationPanel.tsx` 的 `timelineHeightCap`）；高度持久化到 `localStorage`
    （`aterm-timeline-height`），`pointermove` 期间只更新内存、`pointerup` 才落盘，与宽度
    手柄同一套 `setX`/`commitX` 两段式（`store/layout.ts` 的 `setTimelineHeight` /
    `commitTimelineHeight`）
  - **双击**分隔条把时间线区整体折叠/恢复（`aterm-timeline-collapsed`，同样的两段式：
    `setTimelineCollapsed` + `commitTimelineCollapsed`）；折叠时高度归零、正文区占满剩余
    高度，但**分隔条本身始终保留、可再次双击恢复**——不会随折叠一起从文档中消失
  - 分隔条本身是 `.conv-panel-content` 常规文档流里的一个真实占位块（不是绝对定位悬浮在
    边界上），天然不会被任何祖先的 `overflow: hidden` 裁掉抓取区——这是从 §6 宽度手柄早年
    "抓取区跨骑在裁剪边界上被裁掉一半"那次教训里直接得出的写法，不重蹈覆辙
  - `cursor: row-resize`；hover/active 态用既有 `--color-accent` 变量变色，不加箭头/圆点等
    图形提示（用户明确要求干净的观感）

**正文**
- 按轮次顺序渲染，用户轮与 Claude 回答在视觉上区分（不同底色/缩进，沿用既有 CSS 变量，不新增调色板条目）
- 保留原始换行，不做其他排版

**面板与标签的绑定**
- 面板内容取决于当前激活标签所属的会话。`Tab` 需**分别保存 `dirName` 与 `rootKey` 两个字段**，供命令直接使用；既有的 `threadKey`（`${dirName}:${rootKey}`）仅用于标签去重比较，**不得靠拆分字符串还原**（目录名本身可能含分隔符）
- 当前标签若为普通 shell（无 `threadKey`）→ 显示空状态提示
- 刷新：顶部按钮手动刷新；标签重新激活时刷新——但**面板折叠时不发起任何请求**：折叠态不
  可见，此刻加载/解析纯属后台空耗（大会话可达数十毫秒），折叠 → 展开时才按需补一次加载
  （若已有对应数据则不重复拉取）；过期响应仍由 `requestIdRef` 生成计数器防护，标签切换与
  面板折叠/展开都会让在飞行中的旧请求失效，细节见 §9 第 4 条

## 7. 测试策略

**Rust（TDD）**
- 正文抽取：字符串型与数组型 content 均正确提取
- 跳过规则各一例：`tool_result` 行、`tool_use` 行、非 user/assistant 类型、`isSidechain`、注入文本、空白轮次
- 会话链跨文件按时间升序拼接
- 缓存命中：大小/修改时间不变时不重新解析
- 真实数据冒烟（临时、只读、提交前删除）：在本机最大会话上验证解析耗时与轮次数量

**前端**
- 时间线按日期分组的纯函数（跨月、跨年、同日多轮）
- 面板折叠状态持久化（含 localStorage 抛异常时的降级）
- 空状态：当前标签无 `threadKey` 时的渲染

## 9. 已确认的代行决定

1. **⌘J** 作为面板开关（⌘B 已分配给左侧边栏）；另加 **Ctrl+Tab / Ctrl+Shift+Tab** 作为
   标签间循环切换（对齐 Chrome），与 ⌘J 复用同一个窗口级 `keydown` 监听器，详见 §6
2. ~~宽度固定 **400px**，不做拖拽~~ ——**已被用户实测反馈推翻**：用户上手用过面板后
   明确要求宽度可调，故加入拖拽调节。新行为：默认仍是 400px，可拖拽范围 [280, 900]px，
   且不超过窗口宽度的 60%；宽度持久化到 `localStorage`，双击拖拽手柄复位到 400px。
   详见 §6
3. 实时跟随**推迟到 P2b**（依赖其文件监听器）
4. ~~面板头部自带折叠按钮（›），折叠后收成 28px 竖条~~ ——**已被用户实测反馈推翻**：
   用户认为两个收起入口（面板自身 + TabBar）冗余，且竖条本身不够干净。改为只保留 TabBar
   一处开关，折叠时面板整体不渲染。连带修正：面板折叠期间不再触发 `readConversation`
   （此前折叠后组件仍挂载、切标签照样后台解析大会话文件），过期响应的
   `requestIdRef` 生成计数器扩展为标签切换与面板折叠/展开两个时机都会推进，逻辑本身
   不变。详见 §6
5. ~~`panelCollapsed` 默认值为 `false`（面板展开）~~ ——**已被用户反馈推翻**：默认展开的面板
   在冷启动时抢占注意力，而多数场景一开始只想用终端。改为默认值 `true`（收起），且只影响
   本地从未存过该偏好的场景——已保存的偏好（无论收起或展开）永远优先，实现细节见
   `store/layout.ts` 的 `readPersistedPanelCollapsed`（用 `v !== null` 区分"没存过"与
   "存过且为假"）。详见 §6
6. **新增：时间线区域整体可拖拽调高 + 双击折叠**（用户反馈：长会话下时间线区占掉太多
   纵向空间，希望能把这块高度让给正文区）——与 §9 第 2 条（面板宽度可拖拽）是同一类"用完
   才发现要调节"的反馈，采用完全相同的两段式持久化模式（`setX` 内存、`commitX` 落盘）以及
   同样的"动态上限现算、不装 resize 监听器"原则，只是维度从宽度换成高度、驱动的字段从
   `panelWidth` 换成 `timelineHeight`/`timelineCollapsed`。与既有的"单个日期分组折叠"
   （§6 时间线小节第 2 条）是两套独立机制，互不影响、互不复用状态。详见 §6
